§7.1 Foundational Principles & Curriculum Scope: Data Acquisition Systems (DAQ): Multiplexing, Sample-and-Hold, and Instrumentation Amplifiers

Unit 7 — Automated instruments and measurement software

Conceptual thread: Make automated experiments auditable and safe. Application scenario: A simulated bench instrument controlled through a local command protocol.

Why this topic matters

Automation can repeat a procedure precisely and repeat a mistake at scale. Instrument state, query ordering, timeouts, metadata and error handling must be designed alongside the measurement. These lessons use local simulated commands; no real instrument control or network access is required. The engineering goal is a measurement whose physical interpretation can survive an independent check. The activity is intentionally model-based: any numbers in assignments, datasets or simulator plots are invented for educational purposes. In actual equipment, frequency-dependent calibration, laboratory safety and environmental ratings would require external evidence.

Learning outcomes

By the end of this unit, you should be able to construct the principal measurement relation and explain its limits; reproduce two independent numerical results; identify at least one coherent alternative explanation for an apparent trend; select the data and metadata needed for a reproducible report; and design a measurement assurance check that does not assume the result it intends to confirm. The last outcome is central: a collection of accurate-looking digital values is not itself a valid measurement.

Suggested sequence

Read the first lesson as a model-building exercise, the second as an instrument or method comparison, the third as an error-analysis problem, and the fourth as a verification and decision exercise. Keep an equation notebook with a units check, an uncertainty table and a record of any assumptions you changed. Then solve the [unit assessment](../assessments/unit-07.html), complete the [integrated project](../projects/unit-07.html) and explore the [interactive model](../simulations/model-07.html).

Model interpretation

The simulator for this unit is Acquisition throughput and command overhead. Idealized single instrument with per-command latency and fixed batch overhead; no genuine SCPI transport. It varies only the mathematical quantities visible in its controls; a plotted result does not constitute an equipment qualification or measured sample. For a meaningful parameter study, save the default values, change one input at a time, reproduce a point independently and then look for a counterexample outside the ideal model. The derivative of the curve, not merely its appearance, is often the best clue about sensitivity and where resolution becomes inadequate.

§7.2 SCPI command parsing and instrument state

7.1 — SCPI command parsing and instrument state

Unit: Automated instruments and measurement software Prerequisites: introductory electronics, calculus, signals and probability. Type of evidence: mathematical and synthetic; no physical hardware was tested. Estimated study time: 75–110 minutes including the calculation and verification challenge.

Engineering question and underlying phenomenon

SCPI is a command-language family used by many instruments, but exact commands, state persistence and transport settings depend on the device. A command that changes range may invalidate the previous calibration selection or trigger status. Queries can return old data if the program assumes instantaneous completion. A robust client treats the instrument as a state machine with a documented initialization and cleanup procedure.

Within this unit, the example application is a simulated bench instrument controlled through a local command protocol. A useful outcome is not merely a number: the reader must be able to decide what electrical or physical quantity is inferred, how the inference depends on a reference, and which alternative mechanisms might reproduce the observation. A calibrated indication is still conditional on the quantity being measured, reference range, environmental state and acquisition protocol. Consider whether the experiment will distinguish the input phenomenon from the measurement chain itself. If not, a second observable or controlled intervention is required.

Governing model

Central relation: Example conceptual sequence: reset or known preset → select function/range → configure trigger → initiate → wait for completion → read → check error queue.

Interpret every mathematical symbol before substitution. Express frequencies in hertz, durations in seconds, temperatures in the convention required by the equation, and angles in degrees or radians as specified. When an inverse operation is needed, verify that it is unique over the operational range. For ratio measurements, verify that the denominator cannot approach zero; for logarithmic levels, identify the reference quantity, detection bandwidth and impedance convention. More reported digits cannot compensate for an undefined physical variable.

Model development

Classify the relation as a direct physical law, an approximation derived under controlled assumptions, or an empirical calibration curve. Write the independent and dependent variables and check the direction of the physical mechanism. In particular, look for a relevant limiting case: no input, very large impedance, long observation, or an ideal reference.

Specific context: An automated measurement is a sequence of instrument-state transitions and evidence artifacts, not a string of commands that happens to run once. Every retry and exception needs a policy before the run begins. Even when the equation is correct, it is valid only under its stated physical model. A good laboratory report differentiates assumptions adopted to make a model solvable, experimentally checked operating limits and parameters that remain completely unknown. The first two can be defended; the third must be stated as an unresolved source of uncertainty rather than assigned an attractive but unjustified small value.

Detailed worked calculation

A simulated DMM accepts :CONF:VOLT:DC 10 and :READ? but will issue an error if READ is requested without a configured function. This is a teaching mock-up, not a promise of syntax for a particular model.

Interpretation. This calculation is a model prediction under the stated conditions, not a newly observed experimental result. To audit it, write the substituted numbers next to their units, calculate without premature rounding, and estimate the order of magnitude before accepting the final digits. Distinguish a predicted change caused by a controlled parameter from an apparent change caused by sensor gain, instrument timing, filtering or normalization. If the expected sign of a correction is reversed, review the signal flow and physical reference before changing the equation to match the desired answer.

Checks that should accompany the numerical result

First, change one input while keeping the remaining assumptions fixed and confirm the output moves in the physically expected direction. Second, calculate the result through a different arrangement of the same governing law or a limiting-case approximation. Third, state the span over which the model has been calibrated or independently verified. Fourth, document whether the result is meant to represent an instantaneous value, an RMS estimate, an average over a defined interval or a statistical bound. These distinctions affect what can legitimately be compared with a manufacturer's specification.

Important departures from the ideal model

Some real instruments buffer output, require newlines or termination characters, and have model-specific command hierarchies. Sending undocumented reset commands can change safety-relevant output states.

It is useful to classify the departures by where they enter. Errors before conversion can distort the physical input; errors in amplification or digitization change the measured indication; timebase and software errors corrupt event ordering; calibration errors convert an otherwise faithful electrical reading to an incorrect physical quantity. The appropriate check differs across these cases. Repeated acquisition on the same unmodified chain can measure repeatability but cannot expose every persistent bias. In practice one should prioritize a small number of physically plausible error sources over a long, unweighted list of hypothetical effects.

Practical verification strategy

Test commands against a simulator and a version-controlled device profile before connecting a physical bench device under supervision. Use a second method or reference only when its systematic errors are sufficiently independent. Record conditions that make the check reproducible: model revision, input data, ranges, reference conditions, clock and sample rate, software version, arithmetic precision and the date of the hypothetical experiment. If equipment were involved, the methods would also need actual safety ratings and personnel authorization. The offline simulations in this book test formulas, not equipment compliance.

§7.3 Timeouts, retries and idempotent acquisition

7.2 — Timeouts, retries and idempotent acquisition

Unit: Automated instruments and measurement software Prerequisites: introductory electronics, calculus, signals and probability. Type of evidence: mathematical and synthetic; no physical hardware was tested. Estimated study time: 75–110 minutes including the calculation and verification challenge.

Engineering question and underlying phenomenon

Communication timeouts are ambiguous: the device may have executed the command but the response may be lost. Blindly resending an initiation command can trigger two acquisitions or advance a sequence. Queries, configuration commands and potentially destructive operations have different retry semantics. The acquisition protocol should correlate each requested operation with an identifier and preserve raw communication logs without exposing credentials.

§7.4 Calibration metadata, provenance and schema design

7.3 — Calibration metadata, provenance and schema design

Unit: Automated instruments and measurement software Prerequisites: introductory electronics, calculus, signals and probability. Type of evidence: mathematical and synthetic; no physical hardware was tested. Estimated study time: 75–110 minutes including the calculation and verification challenge.

Engineering question and underlying phenomenon

A data file can be complete and still lack a defensible link to the measurement system that produced it. Essential metadata include units, sensing channel, timestamp clock source, calibration record identifier, range, revision, environmental conditions and processing versions. Store raw samples immutably; transformations should produce derived datasets with a reproducible lineage. A checksum detects changed bytes but cannot establish that the calibration record was correct.

§7.5 Automated test validation and regression checks

7.4 — Automated test validation and regression checks

Unit: Automated instruments and measurement software Prerequisites: introductory electronics, calculus, signals and probability. Type of evidence: mathematical and synthetic; no physical hardware was tested. Estimated study time: 75–110 minutes including the calculation and verification challenge.

Engineering question and underlying phenomenon

An automatic test should verify both scientific behavior and software behavior. Unit tests check mathematical functions; integration tests check command ordering and parser behavior; regression data can catch unintended changes. A simulated instrument cannot validate real wiring, range safety or actual calibration. The strongest tests intentionally provoke invalid inputs, out-of-order events, dropped samples and stale state, rather than exercising only one normal run.
