# Information Security — Unit 8: Security Assurance, Secure Development and Responsible Testing

**Learning outcomes.** Translate risks into testable assurance claims; design secure development evidence throughout a product lifecycle; distinguish static analysis, dynamic testing, review, and formal methods; evaluate the limits of penetration testing; and carry out coordinated disclosure through authorized, responsible channels. The culminating project uses synthetic data and isolated models only.

## 8.1 Secure development: assurance as a chain of evidence

A system is not secure because a team declares that security was considered or because a dashboard displays green checks. Assurance is an argument that specific properties hold under stated assumptions, supported by evidence that can be inspected and challenged. A security requirement should be precise enough that a tester can determine whether it is satisfied. 'Protect student data' is too vague to support a meaningful acceptance test. 'A user without a current course assignment cannot retrieve or export another student's unpublished marks, including through bulk endpoints and background jobs' names actors, resources, actions, and exceptional paths. The second requirement can generate positive and negative tests, code review questions, and operational monitoring expectations.

Threat modeling should start at design time but continue as a product changes. Represent assets, trust boundaries, identities, data flows, privileged operations, and credible ways those elements could fail. Record why a boundary exists and what happens if it is crossed. A change that sends student assignments to a new analytics service creates a trust relationship even if the visible frontend is unchanged. A change in authentication-provider configuration can affect every service trusting that provider. The model should be updated when architecture or processing purpose changes, not only before the first launch. Keep the model focused enough that engineering teams can use it in ordinary decisions.

The NIST Secure Software Development Framework provides practices for preparing an organization, protecting software, producing well-secured software, and responding to vulnerabilities. OWASP ASVS supplies testable security requirements for modern web applications and services. These references serve different but complementary purposes. SSDF addresses development practices and organizational process; ASVS supports verification of application controls. Neither is a magic certificate. A product can follow many good practices and still contain a novel flaw, while a small product may satisfy well-chosen controls without generating hundreds of ceremonial documents. Evidence should identify the precise standard version, applicability, exceptions, and tested outcome.

Secure code review examines how actual operations occur, not just whether dangerous function names appear. Reviewers should trace data from untrusted sources through parsing, validation, authorization, transformation, storage, and output. They should inspect privileged operations, business invariants, external calls, and error handling. An input parser can be correct while an authorization check is missing; a flawless encryption call can store its key in publicly accessible configuration. Pair automated tools with human reasoning focused on high-impact boundaries. Static analysis is especially useful for repeatable patterns but may produce false positives or miss architectural flaws and business-logic assumptions.

Automated testing should include misuse-resistant defaults and meaningful negative cases. A test that confirms an administrator can update a record is necessary but insufficient; verify that an ordinary account cannot update that record and that the denied request leaves storage unchanged. Test boundaries at expiry, missing attributes, revoked membership, malformed data, concurrency, and dependency failure. In CI, isolate secrets, grant minimum permissions, pin trusted actions appropriately, and preserve reproducible build evidence where feasible. Treat the build pipeline as part of the product's privileged environment; compromised build credentials can invalidate otherwise careful source review.

Release decisions need a clearly defined owner. A high-risk defect found one day before launch should not be silently categorized as 'known issue' without acceptance by an accountable authority. Document impact, affected population, possible mitigations, test results, dependency versions, and rollback plan. Conversely, endless attempts to achieve perfect security can prevent important beneficial services from operating. The proper decision weighs residual risk against legitimate use under transparent constraints. Do not confuse 'no findings from a scanner' with 'no security risks'; absence of a tool's findings says only what that specific method detected under its current coverage.

**Example acceptance case.** A library platform introduces a feature that allows lecturers to share unpublished feedback. The design specifies authorization based on assignment, encryption during transport, minimal logging, expiry of share links, and deletion after the retention period. Before release, tests include two lecturers with different course assignments, a student who is not enrolled, an expired share link, a revoked assignment, a failed log collector, and a restored backup. A manual review checks whether the share link is included in analytics or error reports. The release evidence links each requirement to its result, not merely to a checkbox labeled 'security complete.'

## 8.2 Penetration testing: scope, authorization, and interpretation

Penetration testing attempts to identify exploitable weaknesses in an agreed environment within explicitly authorized boundaries. Ethical authorization is not optional just because a system is reachable on the public internet. A professional engagement needs a written scope describing the target systems, identities, permitted techniques, prohibited activities, schedule, contact points, evidence-handling rules, and emergency stop process. For an academic laboratory, the safest starting point is a deliberately vulnerable local training application or synthetic system controlled by the participants. Unscoped scanning and attempted access to third-party resources are not necessary to learn threat modeling or validation methodology.

Different assessment methods answer different questions. A configuration review can reveal broad privileges; source review can find missing authorization branches; dependency analysis can flag unsupported packages; automated dynamic testing can discover selected runtime behaviors; a penetration test can demonstrate consequences through controlled verification. None proves the absence of all vulnerabilities. Coverage depends on tester skill, budget, time, credentials, system state, and whether important business paths were exercised. An organization that treats one successful test as timeless assurance may ignore rapid product changes, stale dependencies, and authorization exceptions introduced afterward.

The assessment process should be risk-aware and evidence-driven. Start with scope confirmation and a jointly approved inventory. Review architecture and existing security controls before executing any active tests. For each suspected weakness, document the expected protective invariant, the observed deviation in the test environment, and the narrowly bounded verification needed. Avoid unnecessary data extraction, service disruption, and persistent changes. Test artifacts should be synthetic wherever possible. The tester should be able to reproduce the observation without retaining other users' sensitive data. A useful finding distinguishes demonstrated behavior from possible downstream harm; the latter may require assumptions not yet verified.

A typical finding describes affected component and version, preconditions, evidence, potential consequence, severity rationale, reproduction under authorized constraints, and remediation recommendations. Reviewers should not confuse an automatically calculated severity with guaranteed business impact. A path that exists only in a local development profile may have lower production exposure, while a missing object-ownership check on an academic transcript endpoint can have severe consequences despite minimal technical complexity. Good findings remain understandable to engineers who must fix them and to owners who must decide priority.

Retesting must verify both the specific defect and the larger invariant. If an application denies a particular unauthorized URL but still allows a bulk export of the same records, a superficial retest might call the issue fixed while the underlying defect persists. Regression tests should exercise equivalent code paths, status changes, and roles. After remediation, verify that necessary legitimate features still work; denial-only systems are not successful applications. Record the deployed build or commit and the tested environment. A fix verified only in staging does not establish that the same correction is deployed everywhere.

Reporting should be respectful of operational risk. If a test accidentally exposes real confidential records, stop, follow the agreed reporting channel, preserve only the minimum evidence needed, and avoid broad publication. A tester's authority does not extend beyond the written scope because the finding appears interesting. Coordinated notification of the owner allows the organization to assess and remedy harm. The professional standard is to produce enough evidence for correction without maximizing access or publicly humiliating the affected parties.

## 8.3 Formal analysis: precise claims in a limited model

Formal methods express systems and desired properties mathematically so that logical consequences can be checked. They are especially useful for critical state machines, access-control rules, protocol assumptions, and transaction invariants. Formal analysis is neither universally necessary nor infallible. A proof applies to a specified model under specified assumptions. If a real implementation omits an operation, uses a different integer width, or depends on an unmodeled external service, the proven property may not transfer. Good assurance therefore connects the model to implementation evidence and states clearly what was intentionally abstracted away.

Safety properties say that something bad never occurs, for example 'no user without permission can receive a protected record' or 'a reservation is never charged twice.' Liveness properties say that something good eventually happens under stated fairness and availability assumptions, such as 'every accepted job eventually reaches a terminal state.' These properties are not interchangeable. A system that denies every action may satisfy a narrow confidentiality safety property while failing essential liveness and usability requirements. A system that always eventually processes a request may violate confidentiality while remaining responsive. A well-designed specification treats necessary safety and progress conditions together.

Finite-state models are good educational starting points. Suppose a document has states Draft, Submitted, Approved, and Archived. An editor may submit Draft, a reviewer may approve Submitted, and an archivist may archive Approved. A transition from Draft directly to Approved should be rejected if policy requires prior submission and independent review. Authorization becomes part of transition guards; each guard checks the actor, object ownership, and current state. A model checker can enumerate all sequences for the small model and verify that forbidden states are unreachable. This is more precise than informal statements that 'users follow the correct workflow.'

Concurrency produces failures that are difficult to see with sequential tests. Two reviewers may try to approve the same action while a revocation arrives; two clients may try to reserve the last available instrument. A database transaction can maintain an invariant such as 'available inventory never becomes negative' if concurrency control is configured and used correctly. But a transaction alone does not solve missing business authorization. Formal state reasoning can identify combinations of interleavings worth testing. A model that assumes every operation is atomic when the real system performs multiple distributed calls may prove a property that the implementation cannot preserve without additional coordination.

Probabilistic analysis addresses properties with uncertainty rather than absolute logical exclusion. A security system might estimate the chance of a random token collision or the probability that a detection alert is a true incident under stated statistical assumptions. These models are sensitive to base rates, independence assumptions, and adversarial adaptation. A probability derived from uniform random draws does not apply to poorly generated secrets. A detector's laboratory confusion matrix does not necessarily predict adversarial traffic months later. Mathematical calculations should accompany explicit limitations and, where possible, empirical sensitivity analysis.

An assurance case assembles claims, arguments, and evidence into a structure that can be reviewed. For example, the top-level claim 'only authorized people can retrieve unpublished work' might rely on subclaims about trusted authentication assertions, complete server-side authorization, correct object ownership, secure session expiry, and the absence of unprotected export paths. Evidence might include design reviews, policy tests, static analysis, and a targeted authorized assessment. Each item should state a test date, code version, relevant environment, and limitations. A reviewer can challenge assumptions and demand missing evidence. This is more scientifically honest than a generic percentage labeled 'security score.'

## 8.4 Responsible disclosure and verification culture

Vulnerability disclosure is an important social and technical process. A researcher who observes a suspected defect should first determine whether testing is authorized and which reporting channel the affected organization provides. Some organizations publish vulnerability disclosure policies or coordinated programs; others may not. When permission is unclear, keep activity to lawful, non-invasive observations and avoid accessing or retaining private data. Report the minimum reproducible evidence, expected consequence, and conditions under which the issue was observed. The goal is to make remediation possible while minimizing accidental harm.

A helpful disclosure report has a concise factual title, affected service or version, observed behavior, expected behavior, environmental details, security impact under explicit assumptions, and safe reproduction guidance. It should distinguish a confirmed weakness from a hypothesis. Researchers must not exaggerate severity to gain attention, claim access they have not demonstrated, or publish private data as proof. Where relevant, provide a clear way for the organization to request additional technical details through a secure channel. The organization should acknowledge reports, triage respectfully, communicate constraints, and investigate even when a claim initially seems unlikely.

Coordinated disclosure timing is context-dependent. A defect that presents immediate harm may require different escalation than a low-impact misconfiguration, and policies, contracts, and applicable laws can constrain action. Neither instant public release nor indefinite silence is universally appropriate. Transparent decisions should account for risk to users, availability of fixes, active exploitation evidence, and the need to inform affected parties. When a disagreement arises, maintain accurate documentation and seek appropriate legal or institutional advice rather than improvising coercive tactics. Technical correctness does not exempt a researcher from consent and data-protection obligations.

Responsible testing culture includes careful language. 'Exploitable' should mean that a harmful outcome was demonstrated or supported by a credible, explicit path; it should not be an automatic label for every unusual error. 'Fixed' should mean that the relevant weakness was corrected in a verified deployed version and that regression checks support the claim. 'No issues found' should mean 'this assessment identified no issues within its defined scope and methods,' not 'the entire system is secure.' Such distinctions are not bureaucratic hesitations; they make security communications reliable, allow fair prioritization, and preserve trust when uncertainty remains.

Educational projects offer opportunities to practice disclosure ethics through simulation. Assign students fictional reports about missing access checks, inconsistent retention, and insecure defaults. Have them write both the initial researcher report and the owner's triage response. They should determine what evidence is necessary, what sensitive information should be omitted, how to estimate likely impact, and how to verify a patch in a controlled environment. This exercise develops real professional competence without requiring attempts against public services or accounts.

**Capstone assurance exercise.** Select a fictional university document-sharing service with readers, contributors, and reviewers. Construct a data-flow diagram, an access matrix, a state machine, and a short threat model. Define at least five specific invariants spanning authorization, data minimization, session expiry, and recovery. Implement automated tests for the invariants in a local mock service. Present one bounded simulation of decision outcomes when a role is revoked mid-operation. Document the observed evidence and every material assumption. A strong submission explicitly identifies what remains unproven, such as runtime dependency integrity or the effects of real-world network partitions, and proposes proportionate follow-up verification.

## Worked questions and complete solutions

### Question 8.1 — Exhaustive state-transition review

A simplified submission object has four states: Draft, Submitted, Approved, and Archived. Allowed transitions are Draft→Submitted, Submitted→Approved, Approved→Archived, and Submitted→Draft for authorized corrections. How many of the 4×4 possible ordered state pairs are disallowed? Explain why counting allowed pairs is not a full authorization proof.

**Step 1: Construct the transition universe.** Four states imply 4×4=16 possible ordered state pairs, including attempts to remain in the same state. The model specifies exactly four allowed state changes. We interpret all other pairs as disallowed transitions; a separate policy could permit explicit no-op requests, but that is not part of the question.

**Step 2: Calculate.** Disallowed ordered pairs =16−4=12. A model-based test can enumerate all sixteen pairs and assert that only the four named transitions pass the state-transition rule.

**Step 3: Explain the remaining proof obligations.** A transition from Submitted to Approved may be allowed by the state machine but must still require an authorized independent reviewer. The state model must also address concurrent operations, consistency of stored state, and whether a user can alter fields without changing the nominal state. Therefore an exhaustive transition-matrix test verifies a useful invariant in a simplified model but does not establish complete application security.

### Question 8.2 — Assurance evidence and coverage

A team defines ten independent security requirements. The team has validated tests covering seven requirements; two have documented but untested designs, and one has no design evidence. Calculate tested-requirement coverage and explain why the number cannot be interpreted as '70% secure.' Propose the next evidence priorities.

**Step 1: Compute the observed coverage.** Seven of ten defined requirements have tests with recorded evidence, giving 7/10=0.70 or 70% requirement-test coverage. This is a statement about evidence organization, not the probability of compromise.

**Step 2: Analyze weighting and validity.** The untested requirements may include the most consequential boundary, such as access to confidential grades, while some tested requirements may be low impact. Tests may also be outdated, run against a staging build, or rely on incomplete negative scenarios. Even perfect coverage of an incomplete requirement set cannot prove the absence of unknown weaknesses.

**Step 3: Prioritize improvements.** Determine the risk criticality of the two design-only requirements and implement bounded negative tests, starting with higher-impact functions. Define and test the missing requirement, confirm the seven existing test results match the shipped version, and examine the threat model for missing properties. Report tested coverage alongside evidence quality and residual unknowns rather than an invented security score.

### Question 8.3 — Concurrency invariant under resource allocation

A laboratory has one remaining microscope available for reservation. Two students submit reservation requests concurrently, each reading that one unit is available. Describe a safe atomic transaction, identify the invariant, and explain why validating availability only in a browser is insufficient.

**Step 1: Define the invariant.** For this simplified inventory, available count A must remain an integer and satisfy A≥0; at most one new reservation may consume the final unit. Both students may read A=1 without error, but granting both would violate the inventory constraint.

**Step 2: Specify atomic behavior.** Use a transaction or compare-and-swap operation that decrements the count only if A>0 and atomically records the successful reservation. Under appropriate isolation, one request succeeds and moves A from 1 to 0; the other sees no available unit and fails without recording a reservation. The exact SQL or service primitive depends on the database, but the semantics require a single atomic decision for the state-changing operation.

**Step 3: State authorization and recovery checks.** Before committing, confirm that the student is eligible to reserve the instrument. Use an idempotency key to prevent retry duplication and test concurrent execution. A frontend check may inform the user, but it runs on a potentially stale view and cannot protect server-side state. If a downstream notification fails after the transaction commits, compensate or retry safely without granting a second reservation. The invariant must survive failure and concurrency, not only one sequential happy-path example.

## Laboratory: build a small assurance case, not a pretend certificate

Create a local service mock with an access matrix and a four-state document workflow. Write a small script that enumerates all sixteen ordered state transitions and reports allowed versus denied outcomes. Add a test for revocation during export and a test for concurrent reservations. Collect test output, version information, and a list of assumptions. Use a safe simulation widget to vary number of requirements and number tested; make it clear that coverage is a measurement of test evidence, not a 'security percentage.' Finally, practice responsible disclosure by writing a fictional report that names the defect and expected behavior without embedding private data or suggesting unapproved access.

**Further reading:** NIST SP 800-218 Secure Software Development Framework and OWASP ASVS 5.0.0. Treat formal results, testing results, and operational observations as complementary evidence, each with stated scope and limitations.
