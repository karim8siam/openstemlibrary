# Unit 1: Web foundations

## 1.1 Urls

A URL is a structured identifier, not a file path to be concatenated casually. Its scheme identifies an interpretation such as https; its authority normally identifies a host and optional port; its path, query, and fragment have different jobs. Consider https://catalog.example.edu/books/linear-algebra?edition=2#proofs. The browser sends the scheme, authority, path, and query information needed to make the HTTP request, but the fragment is resolved locally by the client and is not transmitted as an HTTP request target. The percent encoded form of a byte is not a security boundary; decoding at inconsistent stages can transform apparently different strings into the same downstream identifier. Path segments must be interpreted in the context of the router rather than as a machine filesystem path. A resource can be virtual, computed dynamically, or mapped to a database record. That independence lets resources survive infrastructure changes.

URL normalization must be designed around identity and policy. A hostname is case insensitive in its DNS interpretation, yet a path can be case sensitive on a server. Query parameter ordering can matter to an application even when a cache assumes it does not. A trailing slash may cause a redirect or represent a different route, depending on the server. Imagine an online library that accepts a user-entered return URL after login. If the application trusts every absolute URL, an attacker can direct students to an impersonation site. Allowing only relative paths or validating against an exact trusted-origin allowlist is more robust than looking for a familiar substring. Unicode hostnames and similar-looking letters add another reason to avoid visual checks for trust.

A clean URL design exposes stable concepts. The route /courses/physics identifies a course listing, /courses/physics/books identifies a collection, and /books/42 identifies one resource. Internal database primary keys need not appear in public routes; when they do, that fact provides no access rights. Users can change identifiers manually, so every resource lookup must repeat authorization checks. A developer should document canonical URL forms and redirect policy, test percent encoding of reserved characters, and decide whether case and trailing slash variants consolidate to one response. Search engines and users benefit from stable links, but canonical tags alone do not enforce redirects or resolve duplicate application state. A well-designed URL is a durable interface contract.

To investigate errors, start with two URLs and compare their parsed components rather than treating them as arbitrary strings. The WHATWG URL parser in the browser can resolve a relative path against a base, normalize dot segments, and encode characters. A reverse proxy might then normalize the incoming path differently. Test the complete chain: browser resolution, CDN forwarding, framework routing, and storage lookup. Log a safely redacted route identifier for diagnosis, not full URLs containing access tokens. If a password-reset token is placed in a query parameter, it can leak into browsing history or logs; prefer short-lived single-use tokens and limit their disclosure. What matters is the end-to-end interpretation, not whether one isolated parser appears correct.

### Applied design, experiment, and interpretation

**Case analysis: URL canonicalization in a course library.** A catalog accepts `/book/103?lang=en`, `/book/103/?lang=en`, and `/book/103?lang=en#examples`. Developers must first decide which forms represent the same conceptual resource. The fragment addresses a location inside a representation, so it does not belong in a server-side cache key. The trailing-slash variant might redirect to a stable canonical form, but the application must make that rule explicit. A naive redirect constructed from an untrusted Host header can send users to an attacker-controlled address. A safer implementation uses a configured public origin to construct redirects. The verification plan sends all three forms, checks status and Location, and confirms that the response has stable canonical metadata without redirect loops. It then tests escaped separators and dot segments. The desired result is not merely a tidy address bar: it is one resource identity under the intended security and caching policies.

**Research exercise.** Compare how a browser URL parser and the application router handle `%2F` inside a path segment. Record whether proxies decode the sequence, whether the framework sees one segment or two, and whether authorization is performed on the final interpreted resource. Do not infer safety from one local test because a reverse proxy or CDN may use different normalization. State the deployment chain before concluding that a route is unambiguous.

## 1.2 Http

HTTP offers a common resource interaction language across browsers, APIs, proxies, and servers. A request consists of a method, target, header fields, and optionally content; the response carries a status, metadata, and representation content. The semantics are defined independently of whether the connection uses HTTP/1.1, HTTP/2, or HTTP/3. A GET normally retrieves a representation without requesting a state change; HEAD asks for the corresponding metadata without a response body; POST submits data to be processed in a resource-specific way. PUT represents replacement or creation at a target resource subject to the server's contract. PATCH describes a partial modification whose semantics depend on its media type and endpoint design. The terminology safe and idempotent matters: GET is safe in its intended semantics, whereas idempotence of PUT means repeating an identical request has the same intended effect, not that every log or side effect is magically suppressed.

A successful response does not always have status 200. A POST creating a new resource may use 201 with Location; a successful update with no representation may use 204; conditional retrieval can use 304 to reuse a stored representation. A malformed request may be 400, an unauthenticated request 401, an authenticated but unauthorized request 403, and a missing resource 404. A conflict with current resource state may be 409; precondition failure can be 412. These codes are not decorations. Clients use them to select behavior, recover from failures, and distinguish expected business responses from outages. An API that returns 200 for every result forces each consumer to reinvent error handling and can cause monitoring to miss failures.

HTTP validators and cache controls require special care. An ETag identifies a representation version according to the origin's rules; a client may send If-None-Match to avoid transferring unchanged content, or If-Match to guard a mutation against stale information. Cache-Control public, private, no-store, and max-age influence whether and how a cache reuses responses. A shared cache must not mix personalized pages across students. A response containing private grades should avoid shared caching, regardless of how attractive the performance benefits appear. Cookies carry client-controlled request metadata, which can create session context, but HTTP itself remains a stateless application-layer protocol. The server must deliberately decide which state is trusted.

When debugging a web application, capture the precise request, response, and cache state. If an enrollment button seems to have 'done nothing,' inspect whether the POST returned 201, 409, or 500; whether a redirect concealed the original result; whether a service worker displayed old content; and whether retries produced duplicate orders. Use an idempotency key or application-level deduplication for operations that must not repeat, such as a payment, since POST is not inherently idempotent. This method-specific reasoning is more reliable than treating every HTTP request as a generic message exchange.

### Applied design, experiment, and interpretation

**Case analysis: conditional updates in an assessment editor.** An instructor reads rubric revision `r7`, edits a score description, and sends an update. Meanwhile another instructor has saved revision `r8`. Blindly overwriting the resource would discard the newer change. Instead the API sends an ETag with the fetched representation and accepts a mutation only when If-Match matches the current validator. If it does not, the server returns 412 and offers a merge or reload workflow. A stale update is not an internal server error; it is a predictable concurrency outcome. The status code communicates what the client should do. An implementation that uses POST may also require an idempotency key to avoid duplicate changes after a timeout.

**Research exercise.** Write a timeline with two clients reading revision `r7`, one writing `r8`, and the other attempting a stale write. Test whether the second write is rejected and whether a failed mutation consumes a new revision number. Distinguish resource versioning from transport reliability. Verify that a cache revalidation response does not accidentally authorize a state-changing request. Consult the semantics of validators rather than using a header name without understanding its preconditions.

## 1.3 Browser–Server Interaction

The phrase browser–server interaction hides a pipeline of independently operating components. The user enters a URL or clicks a link. The browser parses the URL, checks security policies, may consult a local cache or service worker, resolves DNS when needed, establishes a connection, negotiates TLS, and sends a request. An edge cache or reverse proxy may answer without reaching the application. If the origin handles the request, its router, middleware, services, and database may each add latency. Once content arrives, the browser parses HTML, discovers subresources, builds document and style structures, performs layout and painting, and runs scripts under event-loop scheduling rules. A page can appear responsive before all subresources complete, and it can look complete while an important interaction remains blocked.

Consider a student opening a simulation exercise from a mobile connection. The HTML arrives quickly from a nearby edge, but a large bundle must be downloaded and parsed before the slider responds. The problem is not necessarily server latency. A waterfall shows the HTML, CSS, JavaScript, font, and image requests. A performance trace shows main-thread work and possible long tasks. The developer should distinguish time to first byte from content appearance and interaction responsiveness. Pushing everything behind client-side JavaScript can harm both low-powered devices and readers without robust script execution; rendering essential explanations as ordinary HTML provides a stronger baseline.

Browsers are active security enforcers, not blind document viewers. The same-origin policy limits direct reading of cross-origin responses; CORS permits selected cross-origin reads, but it is not a substitute for authenticating a user. Mixed-content restrictions limit insecure subresources on secure pages. Content Security Policy can constrain executable sources and reduce some injection consequences; it must be configured and tested rather than pasted as an unexamined header. Cookies with Secure, HttpOnly, and SameSite attributes serve different protective purposes. The server cannot assume that every request came from the intended user interface, because attackers can issue requests directly.

One productive debugging exercise is to reproduce a failing checkout in stages. First verify that the browser produced the intended request and included the expected headers. Next confirm that the gateway forwarded the correct method and request body. Then inspect the service trace, database transaction, and response. Finally check whether the browser's UI transition reflects the response. Use correlation identifiers without logging sensitive session values. Distributed traces are useful only if clocks, sampling, and privacy settings are understood. An end-to-end mental model reveals that many 'frontend bugs' originate elsewhere and many 'server bugs' are actually caching or rendering mismatches.

### Applied design, experiment, and interpretation

**Case analysis: a lesson that loads slowly only on phones.** Laboratory staff measure a 120 ms origin response but students report a 4-second delay before a circuit simulator responds. A browser trace shows a compressed 550 KB script that takes 1.8 seconds to parse and execute on a low-powered phone, followed by a heavy canvas initialization. The server metric is accurate yet insufficient. The team splits the simulator from the text reader, shows a static explanation immediately, and initializes the interactive canvas only after the relevant chapter is opened. Reserved layout dimensions prevent the controls from displacing the reading position. Resource timing and main-thread traces provide evidence that the change helped.

**Research exercise.** On a controlled throttled environment, capture TTFB, FCP, long tasks, and time to usable slider. Change only one dimension at a time: route chunking, script deferral, or image loading. If the result varies across runs, record distributions instead of cherry-picking a favorable trace. Also verify keyboard operation under throttling; a visible slider that cannot respond is not interactively ready.

## 1.4 Document Models

An HTML document is a structured representation of meaning, not just a set of rectangles. Parsing creates a Document Object Model, or DOM, whose nodes represent elements, text, attributes, and relationships. The DOM can be modified by scripts, yet the initial source remains important for accessibility, search discovery, and graceful behavior. Semantic elements such as header, nav, main, article, section, button, and form communicate intended roles. They are not interchangeable with visually styled div elements. A button has focus and keyboard activation behavior by default; an arbitrary clickable container does not. A heading hierarchy allows readers and assistive technologies to locate a topic quickly. A table expresses tabular relationships, while CSS grid is for layout rather than for pretending unrelated cards are a table.

The browser also constructs style and accessibility representations. CSS selectors determine matched declarations, the cascade resolves conflicts, and the layout system computes geometry. The accessibility tree translates document semantics and state into information used by assistive technology. It is possible for a page to look polished but expose meaningless control names, or to read correctly in screen-reader order while the visible order has been rearranged in a confusing way. DOM order should usually correspond to reading and keyboard order. Using CSS to reverse a logical sequence without revisiting keyboard flow creates a subtle usability defect.

Suppose a physics course page contains three experiment panels, each with a temperature slider and a graph. Give each slider a programmatically associated label and output, and describe the graph with a concise text summary. When a student's result changes dynamically, update the explanation in a way that does not overwhelm live regions with every animation frame. Preserve a text alternative when the graph cannot render. These requirements are not merely compliance labels; they force the author to decide what the experiment actually teaches and what changes in response to input.

Modeling document structure before styling reduces rework. Define navigation destinations, landmarks, headings, forms, validation messages, and disclosure controls. Only then choose responsive layouts. Test the document using keyboard-only navigation, zoom, reduced motion, and narrow viewports. A responsive implementation changes geometry, not essential meaning. If the interface becomes unusable at 200 percent zoom, that failure often reveals a brittle layout model rather than a shortage of media queries. A reliable document model is a public contract between content, interaction code, and diverse reading technologies.

### Applied design, experiment, and interpretation

**Case analysis: building a textbook chapter reader.** An author initially represents each section as a card of nested divs, with headings simulated by bold text. Visual screenshots look correct, but the document has no navigable heading outline or landmarks. Replace presentation-only structure with main, nav, article, section, h1–h3, and figures. Worked solutions can use details elements when a simple disclosure interaction meets the requirement. The simulation's canvas needs an adjacent explanation and a control group with explicit labels and units. The graph should expose key values in ordinary text. These changes preserve styling flexibility while improving the document contract.

**Research exercise.** Inspect the browser accessibility tree for the original and revised chapters. Count landmarks, usable headings, labeled controls, and keyboard-reachable actions. Render each chapter with JavaScript disabled and evaluate whether the scientific claims remain discoverable. A document with semantic nodes can still have misleading text, so supplement structural checks with an actual reading-order review.

### Integrated laboratory: trace the life of a chapter URL

Design a reproducible experiment around a chapter URL such as `https://library.example.edu/course/physics/unit/3?print=1#exercise-2`. The first goal is not to implement the page but to describe what each component means. Record the scheme, authority, path, query string, and fragment. Change the fragment alone and predict whether a new HTTP request is necessary. Change the `print` query value and explain why the server might select a different representation. Replace a path segment with an encoded reserved character and record what happens at each decoding boundary. The question is not 'which spelling looks nicest?' but 'which names identify the same resource under this contract?'

Next trace one ordinary navigation. Use browser developer tools with caching temporarily disabled. Capture whether DNS resolution and connection setup are visible, whether the request uses an existing connection, which method and target are transmitted, and which response headers determine content interpretation. Inspect the resulting HTML source and compare it to the live DOM after scripts run. A DOM node introduced by client code does not magically exist in the server's original HTML. Identify one element that should be available to readers with scripts disabled and one that legitimately requires a working interactive runtime.

Introduce controlled failures. Request a nonexistent unit and confirm the HTTP status is genuinely 404. Request a protected teacher-only page as a student and inspect how the server handles that failure without exposing a secret. Disable one JavaScript resource and observe whether the article remains readable. Simulate a poor connection and explain why the browser might show text before an embedded graph. Keep a timeline of observations rather than inferring transport behavior from an application's visual appearance. Modern browsers may serve content from a service worker or local cache, so make the cache state explicit before interpreting the trace.

Write a brief architecture diagram with four boundaries: user agent, network/edge, application server, and data sources. Label which boundaries can cache, authenticate, authorize, and render. They are different capabilities, not universal obligations of every component. A static chapter may be served entirely from an edge; a student-specific completion record should require appropriate identity context. Your report should have the test URL, request/response evidence, DOM observation, failure experiments, and one independently justified improvement.

For the final reflection, imagine the same page in a low-bandwidth rural classroom. Which information must be available immediately, which components can load lazily, and which network requests can be eliminated altogether? Treat such constraints as real user requirements. If the exercise is conducted against an existing production service, do not send hostile or high-volume traffic; use a local teaching environment. This laboratory develops a habit of tracing actual behavior from URL through network to document representation before prescribing architectural changes.

### Synthesis: resource meaning across the request lifecycle

A resource address begins as a human-facing navigation promise and ends as an interpreted request inside a routing and rendering system. Study the phrase 'the same page' critically: two URL spellings may select the same server document; a cache may store two copies; a browser fragment may point to two different reading positions; and scripts can dynamically change what appears within an unchanged document. These differences explain why canonical URLs, request identity, and document state must be modeled separately. In a university library, a chapter permalink should remain intelligible after changing infrastructure, while a private session-specific progress indicator can change without changing the public resource identity.

Before proceeding, draw a sequence that names the component responsible for each decision. The browser resolves and parses, the network transports, the HTTP server interprets method semantics, the application enforces permission where required, and the browser finally renders a representation. Proxies or caches may intervene. A useful correctness test changes one dimension—query, fragment, authorization, cache freshness, or script availability—at a time and records the response. The exercise exposes hidden assumptions: a successful HTTP response might still be inaccessible, a page that looks unchanged might have a stale ETag, and a fragment link can work without any new request. The learner should be able to explain those observations without using the vague claim that 'the server loads the page.'

## Worked questions

### Decompose a chapter URL

For https://learn.example.edu:8443/units/3?lang=en&mode=print#example-4, list each URL component. Which part is not transmitted as the HTTP request target? Explain one security consequence of using user-supplied redirect URLs.

**Parse the identifiers.** The scheme is https; the host is learn.example.edu; the explicit port is 8443; the path is /units/3; the query is lang=en&mode=print; and the fragment is example-4. The browser understands the authority from the host and port. The exact request-target form depends on the connection context and HTTP version, but the application receives the path and query information necessary to select a resource. Splitting by a slash character without URL parsing is not sufficient because syntax includes escaping and relative resolution.

**Identify transmitted material.** The fragment is a local reference into the returned representation and is not ordinarily transmitted to the origin in an HTTP request. Changing only #example-4 to #example-5 can update the browser's local location without retrieving new document content. Query parameters have different semantics: they can affect the server's selected representation and therefore can affect cache identity. This distinction matters when debugging apparently duplicate requests or canonical links.

**Address the trust boundary.** If a login process accepts an arbitrary return URL, a malicious page could cause the user to be redirected to a lookalike host after authentication. Avoid open redirects by using validated relative destinations or an exact trusted-origin allowlist, and construct server redirects from configured origins rather than an untrusted incoming Host header. The correct solution describes both representation identity and authority; parsing a syntactically valid URL does not imply that its destination is trusted.

### HTTP precondition reasoning

Two editors read an assessment rubric at revision 7. Editor A writes revision 8. Editor B sends an update based on revision 7 using If-Match: "r7". What should the server do and why is unconditional overwrite incorrect?

**Describe concurrent state.** Both editors initially observe the same representation. A successfully commits a change, so the authoritative rubric is now revision 8. B's intended change is based on older information, not the current record. Blindly accepting B could discard A's work without either editor noticing. This is a lost-update problem rather than a simple HTTP syntax problem.

**Evaluate the precondition.** If the server correctly binds its ETag validator to the current representation, B's If-Match: "r7" precondition is false after A's update. For an otherwise valid conditional request, the server should reject the update with 412 Precondition Failed rather than silently applying stale data. The client can fetch the new representation and invite B to resolve the conflict.

**Check the full contract.** The server must evaluate the precondition atomically with the mutation, otherwise a race remains. The ETag should reflect a representation version with a precise validator contract. Repeated requests after a timeout also require thought about idempotency and side effects; merely adding an HTTP header to the frontend will not implement optimistic concurrency if the persistence layer ignores it.

### Locate the page delay

A chapter takes 120 ms to respond from the server, 350 ms to download additional assets, and 1,500 ms to initialize the interactive model on a mobile CPU. Estimate a naive sequential total, identify its limitations, and propose a testable remedy.

**Compute the illustrative sum.** Under the deliberately simplified assumption that these stages run sequentially and do not overlap, the total is 120 + 350 + 1,500 = 1,970 ms. This is not a real-browser performance guarantee: connection setup, parallel downloads, main-thread scheduling, style/layout work, and overlaps can change the observed timeline. A trustworthy diagnosis uses an actual trace to determine which stages are on the critical path.

**Identify the bottleneck.** The largest listed component is model initialization at 1,500 ms, about three quarters of the illustrative total. Optimizing only the server's 120 ms response cannot remove most of this delay. One candidate change is to render the textbook explanation as static HTML and initialize the simulator only after it is needed, ideally with a readable fallback.

**Plan the evidence.** Measure content appearance and time to first usable control before and after the change on representative mobile hardware. Inspect JavaScript long tasks and ensure lazy initialization does not trap focus or start too late after the student requests an experiment. Report both median and tail behavior across repeated runs. The desired outcome is a usable learning page, not merely a lower server processing number.
