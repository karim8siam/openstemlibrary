# Unit 1: Parallel models and the shape of a computation

## 1.1 Shared Memory

Parallel computing begins with a distinction between a program's *meaning* and the order in which its operations happen. A sequential algorithm describes a chain of operations in which the next step may depend on the result of the previous step. A shared-memory parallel program permits multiple instruction streams to operate on a common address space. The address space might be physically served by a single memory controller, by caches connected through a coherence protocol, or by several memory domains that are accessible using the same pointer notation but with different latency. Sharing an address space does not imply that every core observes changes at precisely the same instant. It merely supplies a common naming mechanism. Ordering and visibility require an explicit synchronization contract.

Imagine processing a satellite image of twelve thousand rows. A straightforward blur reads each pixel's neighborhood and writes a corresponding output pixel. The computation can be divided into contiguous row ranges, each handled by one worker. This is a good shared-memory example because the input array is read-only during the blur and each worker owns non-overlapping output rows. The ownership rule makes the inner loop free of write-write races. There remains a boundary condition: for a three-row filter, a worker must read a row slightly outside its own output range. That is not a race while the input is immutable. A more dangerous implementation writes the blurred image into the input array. Then one worker can read a neighbor already modified by another worker, making results depend on schedule order. Double buffering is a correctness technique, not merely a performance optimization.

A useful cost model distinguishes computation, data movement, and coordination. If an operation requires W arithmetic steps and the machine can sustain r useful steps per second per worker, the ideal compute time with p workers is W/(pr). But a real program also pays for memory traffic, task setup, and synchronization. If each output pixel consumes several input bytes and produces four output bytes, the required memory-bandwidth traffic may grow faster than instruction throughput. Once the shared memory bus saturates, doubling workers cannot double throughput. The simplest roofline argument compares arithmetic intensity I, measured in operations per byte transferred from the relevant memory level, against available bandwidth B: sustainable arithmetic rate cannot exceed I times B. A compute-bound kernel benefits from wider execution resources; a bandwidth-bound kernel benefits primarily from reducing transfers or increasing effective locality.

The phrase 'shared memory' is ambiguous across hardware and APIs. On a multicore CPU, global memory is coherent in a way defined by the architecture and language memory model. Within a GPU workgroup, 'shared memory' can refer to software-managed on-chip storage visible only to threads in that block. A GPU's device-global memory is larger, with different access and synchronization costs. A student must identify which memory space the program actually uses instead of assuming the same word has one universal performance meaning.

Non-uniform memory access, or NUMA, further complicates the common-address abstraction. Consider a two-socket server in which each socket has its own attached memory channels. A core can usually read remote-socket memory, but doing so may incur additional latency and interconnect traffic. If the operating system places all pages on socket A and half the workers on socket B, the program can suffer remote accesses despite using perfectly legal pointers. First-touch allocation, careful affinity, and a measured policy for allocating working sets can improve locality. These techniques depend on the hardware topology and should be benchmarked rather than treated as universal speedup switches.

Synchronization enforces relationships among accesses. A mutex protects a critical region and orders participating updates, but excessive locking can serialize the computation. An atomic increment may suit a small counter, but thousands of workers contending on one atomic memory location will still fight for the same cache line. A barrier ensures that a group has completed one phase before entering another; it does not repair a race inside a phase. The right design often avoids contention by giving each worker a private partial result and combining those results in a controlled reduction. A good ownership argument identifies which worker may write each location, which workers may read it, and what establishes the happens-before relation when ownership changes.

A practical examination starts by drawing the memory layout. Mark input arrays, output arrays, scratch buffers, and per-worker state. For every array, record whether reads are concurrent, whether writes can overlap, and whether a synchronization point separates dependent phases. Then count the bytes crossing the slowest important memory boundary, not merely the number of source-code loads. CPU caches can reuse adjacent elements and may make an explicit shared-memory algorithm far faster than the naive traffic count, while irregular pointer chasing can defeat that reuse. A final test should vary worker count and problem size independently: if time barely changes with p for a tiny image, scheduling overhead may dominate; if time stops improving for a very large image, bandwidth or NUMA effects may dominate.

Shared memory is an engineering choice, not an excuse to omit synchronization. Its strength is low-friction data sharing and flexible fine-grained work. Its main risk is hidden coupling through mutable state. Use shared memory when the data fits in an accessible address space and the program can describe ownership cleanly; prefer explicit communication when independent address spaces provide better scalability or isolation.

## 1.2 Message Passing

Message passing replaces shared address locations with explicit communication between independently executing processes. Each process owns a private memory space and exchanges values through send, receive, or collective communication operations. In a distributed-memory cluster, two processes may reside on different servers and cannot simply dereference each other's pointers. A send names a communicator or channel, destination and message contents; a matching receive chooses the values that arrive. The visible contract includes ordering, progress, matching rules and whether the call blocks. It does not guarantee that the network itself has zero latency or infinite buffering.

Consider a weather model that divides a rectangular grid into sixteen tiles. Each process updates its own tile by reading neighboring cells. Interior cells need only local memory; cells along a tile boundary need the previous time-step values of adjacent tiles. The processes therefore exchange *halo* or *ghost-cell* values. A well-designed iteration sends halo data and then computes interior cells while communication progresses, followed by a wait and boundary update. The legality of overlap depends on the implementation and available progress mechanisms; merely launching a nonblocking request is not proof that the network advances concurrently with computation. If the program overwrites a send buffer before completion, the receiver may obtain incorrect data. If it updates boundary cells before the receive finishes, it reads stale ghost values.

An elementary message cost model is T_msg = alpha + n beta, where alpha represents fixed startup latency, n the message payload size in bytes, and beta the time per byte. This model exposes why sending a thousand tiny messages can cost much more than one suitably batched message. For illustration, if alpha is 25 microseconds and beta is one nanosecond per byte, a 1,000-byte message costs about 26 microseconds, while a 1,000,000-byte message costs roughly 1.025 milliseconds. The numbers are hypothetical and ignore contention, topology, software packing and protocol changes. Real latency and bandwidth should be measured by message size and placement. The alpha-beta formula is a first-order model, not a guarantee that transfer time stays linear indefinitely.

Deadlock is an algorithmic possibility. Suppose process zero executes blocking send to process one, while process one performs the same blocking send to process zero, and neither posts a receive until its send returns. Whether the code hangs can depend on eager buffering thresholds. A tiny payload might fit an internal buffer, hiding the bug; a large payload can expose it. Correct code should not rely on unspecified buffering. A paired send-receive operation, matched nonblocking operations with explicit completion, or consistently ordered communication protocol can avoid this risk. Protocol design must also prevent accidentally matching a control message to a data receive. Communicators, message tags and source restrictions are correctness tools.

Message passing changes the way data structures are designed. A distributed hash table cannot silently read another process's local bucket; it must request or route the relevant value. A globally sorted array may be stored in contiguous partitions on workers with known ownership. Operations that are local under one decomposition may require all-to-all traffic under another. For example, a row-wise partition favors row-based stencil operations while an FFT transpose may require a global redistribution. Good algorithms minimize expensive global coordination without compromising the mathematical result. This is why domain decomposition and communication topology must be considered alongside arithmetic complexity.

Fault behavior needs careful qualification. Independent processes can isolate address spaces, yet an MPI job may still terminate when a participating process fails unless the execution environment supports a suitable recovery mechanism. Message passing is not inherently fault tolerant. Application-level retries, idempotent operations and checkpointing are separate engineering concerns. An out-of-order message from a previous iteration can corrupt a later one unless a step identifier or ordering rule distinguishes it. Error detection, versioned messages and validation of sizes are especially important when integrating modules written by different teams.

A good performance experiment measures three quantities: useful local compute time, communication time including waits, and imbalance among processes. If one rank handles a dense section of the workload while others finish early, total iteration time follows the slow rank. Communication optimizations may have little effect until that imbalance is fixed. Conversely, a perfectly balanced decomposition can still scale poorly if the surface area of each tile grows large relative to its volume or the application performs a global reduction at every iteration. The communication model explains these bottlenecks more clearly than a single aggregate speedup figure.

Message passing is powerful because ownership is explicit. It can run on a laptop with multiple processes and on a networked cluster, although communication behavior differs. Its costs are serialization, transfer, synchronization, and complexity at boundaries. Use it when memory is distributed or the application benefits from independent processes. State whether the code assumes reliable delivery, ordered messages, identical data formats, and uniform hardware; those assumptions shape correctness more than the choice of library name.

## 1.3 Data Parallelism

Data parallelism applies the same logical operation to many independent data items. A map operation that squares each element of an array is the simplest example, but real scientific applications include vector transforms, image filters, reductions, stencils and matrix operations. The basic design question is whether the output associated with a data item can be computed without reading a value that another worker is currently changing. When the answer is yes, the work is naturally decomposable. When the answer is no, the developer must separate dependent phases, expose a reduction or adopt a more complex communication schedule.

Suppose a laboratory processes ten million independent sensor readings. Every reading must be calibrated using an affine transform y_i = a x_i + b. Assigning equal-sized chunks to workers is straightforward because each output depends only on a known input and fixed coefficients. For n items and p workers, nearly equal static partition sizes are floor(n/p) or ceil(n/p). If n=10,003 and p=8, three workers handle 1,251 items and five handle 1,250. This difference of one is negligible for uniform-cost records. If some readings require expensive outlier correction, however, equal record counts no longer imply equal work. Dynamic scheduling or weighted partitions can improve balance at the cost of greater scheduling overhead and potentially worse memory locality.

Data parallelism is distinct from vectorization. A CPU vector instruction processes several data lanes per instruction; multithreading dispatches independent work to several execution contexts; a GPU launches many lightweight threads with warp-level execution. A program may exploit one or all of these mechanisms. Vectorization needs compatible memory accesses and a loop-carried dependency analysis. For a loop that updates x[i] from x[i-1] in place, iterations are not independent despite looking elementwise. A parallel prefix algorithm can often transform a recurrence into phases of associative combination, but that transformation must preserve the intended operation's semantics. For floating-point addition, changing grouping can change rounded results even when mathematical addition is associative.

Alignment and layout affect performance. Arrays of structures can be convenient for users but may lead a vector kernel to load many unused fields. A structure-of-arrays layout can put the same field for many records in contiguous memory, often improving vector loads and GPU memory coalescing. Yet structure-of-arrays is not universally better: if a kernel uses every field of each object in rapid succession, keeping fields together may improve cache locality on some CPUs. The correct decision follows the actual access pattern and measured traffic. If an algorithm touches 32 bytes per record, processing a million records means at least 32 MB of compulsory data movement before considering cache line overhead or additional passes.

Reductions are a special form of data parallelism because partial work is independent but the outputs must be combined. To sum one million measurements, each worker can compute a local sum and then participate in a tree reduction. A binary reduction tree has logarithmic critical-path depth if enough workers and communication resources exist, whereas writing each partial sum into a single shared accumulator under a mutex can create serialization. This does not mean the tree is free. Its performance depends on startup latency, memory hierarchy and how much useful local work precedes each merge. For reproducibility, the reduction tree may need to be fixed across runs, and numerically sensitive applications may require compensated or higher-precision accumulation.

A useful distinction is between *embarrassingly parallel* computation and a merely parallelizable algorithm. Generating independent Monte Carlo trajectories is embarrassingly parallel as long as each trajectory uses a separate, reproducible random stream and the aggregate estimator can be combined correctly. A finite-difference heat equation is parallelizable but every time step has dependencies on neighboring cells. A graph traversal is even more irregular: the active frontier changes, vertex degrees vary widely, and updating shared visit state may require synchronization. The data-parallel label therefore describes an approach to exploiting independence, not a promise about communication overhead.

Construct a dependency graph to choose a design. Represent each output task as a node and each read-after-write constraint as an edge. If a set of nodes has no edges between them, those nodes may run together, subject to resource and memory limits. Identify whether inputs are immutable, whether partial outputs have unique owners, and whether the combination operator is associative. Then reason separately about the work W, the critical path or span S, and the communication volume. No number of processors can finish in less time than the critical path, and finite bandwidth also establishes lower bounds on execution time.

Data parallelism usually gives the clearest starting point for a new parallel program: split independent items, eliminate accidental shared writes, then profile. Its common failure modes are imbalance from nonuniform items, memory-bandwidth saturation, hidden reductions, and numerical changes caused by reordering. Test each of those before concluding that a parallel implementation is superior because it uses more threads.

## 1.4 Task Parallelism

Task parallelism decomposes a computation by *activities* rather than by equal-sized portions of a dataset. A video pipeline may decode a frame, apply a filter, perform object detection, annotate the result and encode output. Those stages can overlap on different frames, and some stages may fork into parallel branches. A compiler can lex several independent modules while other workers optimize previously parsed modules. The important abstraction is a directed acyclic graph, or DAG, whose nodes represent tasks and whose edges represent dependencies. A scheduler can run any task whose predecessors are complete and whose resources are available.

Two lower bounds help evaluate a task graph. Let W be total work measured in time on one processor, ignoring parallel overhead, and S the length of the longest dependency chain, also called the span. On p identical processors, execution time cannot be less than max(W/p,S). If W=120 milliseconds and S=35 milliseconds, an eight-worker machine has a lower bound of 35 milliseconds, not 15 milliseconds, even before scheduling costs. Available parallelism is approximately W/S; here it is about 3.43. Adding processors beyond that ratio may improve schedule quality under some graphs, but the lower-bound analysis shows why ideal linear scaling is impossible. The critical path often changes when tasks have input-dependent durations.

Consider a scientific data pipeline with independent modules for reading instrument A and instrument B. Calibration of A can overlap with reading B, but a cross-instrument reconciliation step needs both calibrated outputs. If calibration A takes 12 seconds, calibration B takes 18 seconds and reconciliation takes 4 seconds, the dependency-constrained portion takes at least 22 seconds. Making calibration A twice as fast cannot reduce that critical path unless it becomes the slow branch. This is a basic reason to optimize the critical path instead of focusing on whichever task has the largest CPU cost in isolation.

Task granularity creates a tradeoff. A million tiny tasks of a few microseconds each can overwhelm a scheduler that pays several microseconds to allocate, enqueue, steal and retire each task. Coarsening tasks reduces coordination costs but may leave fewer runnable tasks when some finish early. Suppose 1,000 independent images require 2 milliseconds of work each. Giving 10 images to each task produces 100 tasks of roughly 20 milliseconds, which may be a useful balance on eight processors. Giving all 1,000 images to a single task creates no task-level parallelism. Giving each image 1,000 subpixel tasks introduces enormous scheduling overhead for little benefit. The useful granularity depends on variability and the cost of allocating and executing a task, which must be measured.

Work stealing is a common response to unpredictable task duration. Each worker keeps a local deque of ready tasks and attempts to take work from another worker when its own queue becomes empty. Stealing can balance irregular recursive computations such as divide-and-conquer search, but it introduces coordination and changes execution order. Some schedulers favor locality by executing newly spawned subtasks close to their parent; some workloads benefit when large tasks are split earlier. Deterministic output requires explicit handling when tasks update shared results, regardless of how convenient the scheduler abstraction is.

Task graphs also describe pipeline backpressure. If an expensive detection stage processes 40 frames per second but the decoder produces 100 frames per second, a queue before detection grows by approximately 60 frames every second unless arrivals are controlled, frames are dropped, or additional capacity is added. With an unbounded queue, memory usage can increase indefinitely. A bounded queue imposes backpressure on the producer, trading instantaneous throughput for system stability. Scheduling therefore includes resource constraints beyond CPU count: memory capacity, file handles, GPU streams and external service quotas can determine which tasks should run concurrently.

Failure is particularly subtle in a task graph. If a task fails after writing a partial output, retrying it must not duplicate an externally visible side effect. For a pure numerical transformation, recomputation is usually safe; for a task that charges a customer or submits a job to another system, idempotency or transaction semantics are necessary. The graph should state whether completion means successful computation, durable output publication, or mere scheduling acknowledgment. A library's futures and promises help express dependencies but do not automatically implement exactly-once side effects.

Design a task-parallel solution by first drawing dependencies and resource requirements, then estimating W, S and scheduling overhead. Choose task sizes with sufficient work per launch. Measure runnable-task count and idle-worker time rather than assuming that an attractive graph necessarily executes well. Task parallelism complements data parallelism: a pipeline stage may itself contain a data-parallel kernel, and a task scheduler may launch many such kernels. The strongest design matches the computation's dependency structure instead of forcing every workload into one abstraction.
