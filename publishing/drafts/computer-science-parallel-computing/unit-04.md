# Unit 4: Distributed-memory parallel programming

## 4.1 Message Exchange

A process in a distributed-memory program cannot assume that another process shares its ordinary pointers. To obtain remote data, it must participate in a communication operation with defined message contents and matching rules. Point-to-point communication is the elementary building block: a sender offers a buffer of typed values to a destination, and a receiver posts an operation that can accept a compatible message. The MPI family of interfaces defines communicators, ranks, datatypes, tags and communication operations. A rank identifies a process within a communicator, not a physical CPU core. One node may host many ranks, and rank ordering does not by itself describe the network topology.

Consider a ring of four processes that each needs the value produced by its left neighbor. Rank r sends its value to rank (r+1) mod 4 and receives from rank (r-1+4) mod 4. The operation seems symmetrical, but performing a blocking send first on every rank can be unsafe if completion depends on a matching receive that no process has posted yet. Some MPI implementations buffer small messages, so a toy demonstration might appear to succeed and then deadlock when payloads grow. A safer design posts appropriate nonblocking receives and sends before waiting for completion, or uses a combined send-receive primitive designed for such exchanges. The communication pattern itself has to be established independently from timing accidents.

Blocking and nonblocking do not mean the same as synchronous and asynchronous at the application level. A blocking send may return when its send buffer can be reused, not necessarily when the receiver has consumed the data. A nonblocking operation starts a transfer request and immediately gives control to the application, but the caller must preserve buffers and later ensure completion. Some implementations make communication progress in the background; others require further calls into the library. Overlap measurements should therefore be based on the actual system and a timeline, not merely on whether the API name contains an 'I' prefix.

Message matching is a correctness concern. A receive may specify a communicator, source rank and tag. Wildcard matching can simplify flexible work queues, but it also makes message arrival order nondeterministic. If different messages describe different algorithmic phases, a wildcard may accidentally accept a stale or unrelated update. Robust protocols use structured tags or explicit phase identifiers and validate expected counts. Complex communication layers often separate control channels from bulk data channels to reduce ambiguity. Datatype definitions also matter: a process sending 64-bit integers must not be decoded by a receiver expecting a different representation or count without an agreed conversion.

A halo exchange for a two-dimensional grid illustrates why communication and computation must be coordinated. Each rank stores interior cells plus ghost layers. At time step k, it sends boundary cells from the current state and receives the neighbors' values for that same step. It may update cells whose dependencies are local while transfers progress. Once incoming ghosts are complete, it computes the boundary region and prepares the new state. The two buffers or explicit phase indices prevent writing new values over data needed by an unfinished exchange. This protocol is correct only if boundaries, corners and exceptional ranks at the physical edges are handled consistently. Nonperiodic and periodic boundaries have different neighbor relationships.

A message model should count both latency and data size. Exchanging four 16-kilobyte faces may be cheaper than sending 4,096 individual 16-byte updates because the latter repeatedly pays software startup and network injection overhead. Conversely, creating giant buffers can require expensive packing and delay early useful work. The best granularity minimizes time on the critical path, which may involve overlapping several independent messages with computation. Microbenchmarks for one sender and one receiver provide starting estimates but can miss network contention under many simultaneous ranks.

Failures and timeouts have no universal behavior in a basic numerical job. A process that disappears can cause waits or job termination unless the application and implementation provide a recovery protocol. A timeout is not proof that a remote rank has permanently failed; network delays or scheduler pauses can look similar. A production service might need explicit heartbeats, replayable state and safe retries, but such features are separate from the mathematics of message matching. For a scientific batch job, coordinated checkpoint-restart may be more practical than attempting to continue with a missing rank.

To validate a message exchange, run with one rank, two ranks and an odd number of ranks; test uneven partitions and message sizes around protocol thresholds. Verify a global invariant such as the sum of exchanged identifiers or exact ghost-layer checksums. Instrument outstanding requests and buffer ownership. A benchmark that merely completes without deadlock may still receive mismatched or old data, so use values that encode both source rank and iteration number.

## 4.2 Collective Operations

Collective communication coordinates a group of participating processes. Common forms include broadcast, reduction, all-reduction, scatter, gather, all-gather and all-to-all exchange. A broadcast distributes one rank's data to others; a reduction combines values according to an operation; an all-reduction makes the combined result available to every participant. These operations are not interchangeable. Using gather to collect all individual arrays and then summing them at a root may transfer far more data than a reduction that combines partial results along the way. The best collective expresses the true dataflow rather than simply using an API that happens to produce the answer.

A tree reduction highlights algorithmic structure. With eight ranks, suppose each holds one local sum. In the first stage, ranks combine values in pairs; in the second, pairs become groups of four; in the third, a root holds the total. The critical communication depth is three combination stages for an ideal binary tree. A flat protocol in which the root receives one value from each other rank has as many as seven serialized receives, though real implementations can overlap message progress. Tree-based algorithms reduce latency depth for small messages, but large arrays may be better served by segmented or ring algorithms that exploit high bandwidth. Libraries choose among such strategies using topology and message-size information.

Associativity is essential to a parallel reduction. Integer addition within a range that avoids overflow is associative, so a tree can regroup additions without changing the exact mathematical result. Floating-point addition is not perfectly associative because each operation rounds; different reduction trees can return slightly different values. For scientific reproducibility, a fixed communication tree or more accurate accumulation method may be needed. Minimum and maximum reductions are often more stable, but special values such as NaNs and signed zero can complicate semantics. Custom reduction operators must satisfy the required mathematical properties and any type or ordering constraints declared by the interface.

A collective involves compatible participation. If some ranks enter a broadcast while others call a reduction on the same communicator in an incompatible order, the program may hang or behave incorrectly. Even when all ranks call the same function, mismatched counts or datatypes can corrupt data. A control-flow branch based on a rank-local observation can accidentally cause divergent collective ordering. The safe approach is to agree collectively on decisions that change the communication sequence, or to structure phases so every rank knows exactly which collective occurs next. Exceptions and early returns must preserve those invariants.

Global collectives may become a scalability barrier. Suppose every iteration of a solver performs a dot product requiring an all-reduction. If the local computation takes only tens of microseconds, the all-reduction latency can dominate across a large cluster. Pipelined Krylov methods and communication-avoiding variants attempt to reduce or hide synchronization frequency, sometimes introducing additional arithmetic or changing numerical behavior. The engineering goal is not always to avoid any global communication. It is to minimize its effect on the critical path while preserving convergence and error guarantees.

Collective cost depends on both algorithm and network topology. A reduction across GPUs within one server may use a different route from a reduction crossing hundreds of servers. A ring all-reduce can communicate in multiple chunks and use available bandwidth efficiently for large vectors, but its latency steps may be less attractive for tiny messages. A tree may minimize startup depth while using more aggregate bandwidth. The application developer should not hard-code expectations about one universal fastest collective; benchmark at representative process counts and sizes, and record library versions and network conditions.

Use collectives carefully in machine learning. In data-parallel training, workers compute local gradient vectors and use all-reduce or related methods to combine them. If gradients are summed but the optimizer assumes an average, learning rate behavior changes with worker count. If batch sizes differ, a simple mean of per-worker means can weight examples incorrectly; weighted sums divided by the global example count are required. Precision, overflow, straggler behavior and stale updates may also affect convergence. Communication correctness is therefore inseparable from the statistical meaning of the aggregated values.

A sound collective test creates small arrays with known rank-specific values, validates outputs on every participating rank, and uses counts that are not simple powers of two. Then benchmark separately for latency-dominated and bandwidth-dominated sizes. Distinguish communication time from application-level barriers and data packing. This disciplined approach prevents a complex library call from hiding an elementary mismatch in mathematical intent.

## 4.3 Domain Decomposition

Domain decomposition partitions a larger computational domain into smaller regions that can be updated independently except at their boundaries. Structured-grid simulations, finite-element models, spatial joins, image processing and geometric searches all use versions of this idea. A decomposition must satisfy coverage, ownership and boundary consistency. Every interior element must belong to a designated owner; replicated boundary data must have a clear source of truth; and tasks must not accidentally omit or double-count elements. The shape of a partition influences not only balance but also communication cost and the ability to exploit local memory.

A rectangular heat-transfer problem provides a concrete example. Divide a 1,024-by-1,024 grid among sixteen ranks arranged as a four-by-four process grid. Each rank owns a 256-by-256 interior tile. For a five-point stencil, it needs one row or column from each adjacent tile. Interior ranks exchange up to 4*256 values per iteration, while physical boundary ranks have fewer neighbors. The owned work contains 65,536 cells; the halo carries about 1,024 values before accounting for communication protocol details. If each value occupies eight bytes, this is roughly eight kilobytes of neighbor data per iteration for an interior rank. A one-dimensional stripe partition would have a different boundary-to-volume ratio and can be preferable for particular grid shapes or processor counts.

The surface-to-volume relation predicts scaling. For a three-dimensional cubic local subdomain with side length m, volume is m cubed and the surface has approximately 6m squared cells. Their ratio is about 6/m. As local subdomains shrink during strong scaling, communication cost becomes larger relative to useful updates. Increasing the halo thickness for higher-order stencils raises transferred data volume. The ratio does not directly equal runtime because real performance also depends on memory traffic, network latency and overlap, but it provides a fundamental geometric explanation for why finer partitions eventually lose efficiency.

Static geometric decomposition assumes roughly uniform work per cell. This assumption fails in adaptive meshes, sparse finite-element systems and particle simulations with clustered particles. If one rank owns a region with dense physics and another owns mostly empty space, identical geographic area does not imply balanced execution. Weighted partitioning estimates computational cost rather than only cell count. Graph and hypergraph partitioners represent interactions as edges or hyperedges and seek to reduce communication while balancing vertex weights. The resulting partition may be irregular, complicating memory access and visualization; this is the tradeoff between balance and locality.

Halo correctness requires an iteration protocol. In an explicit time-stepping scheme, every rank must compute time k+1 from time k values. Receiving an adjacent rank's new time k+1 values early while others still use time k creates a mixed-time computation unless the mathematical method explicitly allows asynchronous iteration. Double-buffered state and tagged halo exchanges avoid this problem. Corner exchanges require care for nine-point stencils or multidimensional operators whose dependencies include diagonal neighbors. Boundaries may represent reflective, periodic, fixed-value or flux conditions, and each condition dictates distinct ghost-cell values.

Decomposition affects local algorithms too. A rank holding a regular tile can store data in contiguous memory and apply vectorized kernels. An irregular sparse partition may need index indirection that increases cache misses. Some applications reorder vertices to improve locality or group nearby cells into blocks. Such transformations can change communication volume and work scheduling. A good partition objective may combine maximum workload, edge-cut communication volume and memory footprint, rather than minimizing one metric in isolation.

Repartitioning during a run is useful when work distribution evolves. An adaptive fluid solver might refine the mesh near moving shocks, making previously balanced tiles uneven. Dynamic load balancing migrates subdomains or graph vertices. Migration costs include serialization, network traffic, reconstruction of local indices, and rebuilding ghost relationships. Frequent migrations can spend more time moving work than they save. Measure imbalance over several iterations and amortize migration over the expected future benefit. The decision resembles a financial investment: pay a one-time movement cost to reduce repeated future costs.

Test a decomposition with a global checksum or invariant, including uneven N that is not divisible by p. Validate no missing cells, no duplicate owners, and correct treatment of global boundaries. A decomposition that works for power-of-two process counts may hide defects at three, five or seven ranks. For performance, report both global domain size and local tile geometry; saying only that a program used 128 workers is insufficient to understand its communication behavior.

## 4.4 MPI Concepts

MPI is a standard interface for message-passing programs. It describes concepts such as communicators, ranks, point-to-point messaging, collectives, user-defined datatypes, process groups and one-sided communication. It does not prescribe a universal network transport or require that processes execute on separate computers. A parallel program can run several ranks on one workstation and later distribute them across a cluster. The semantic contract belongs to the MPI version and implementation, while achievable performance depends on transport, placement, compiler and system configuration. Contemporary MPI standards include additional facilities for partitioned communication and other advanced patterns, but beginners should first master matching, completion and collective consistency.

The communicator is central. It defines a communication context and a group of processes whose ranks are meaningful within that context. Two libraries can duplicate or split a communicator to prevent unrelated messages from matching accidentally. Ranks are local identifiers; world rank three need not equal rank three in a subgroup. Splitting an application into teams for independent simulation ensembles is easier when each team uses a separate communicator. The program then has to decide how partial results are returned to a parent group, which introduces hierarchical communication design.

A point-to-point message includes matching information such as source, destination, tag and communicator. A sender may use a derived datatype to describe strided or structured memory layouts instead of manually packing every field. This can improve clarity and sometimes performance, but type extents, alignment and portability must be checked carefully. A buffer of ten records should not be interpreted as ten bytes or vice versa. When workers use heterogeneous environments, portable representations and explicit type contracts matter more than assumptions about native structure layout.

The blocking/nonblocking distinction is only one axis of MPI semantics. Completion of a send may mean its original buffer is safe to reuse, while receive completion establishes that the receive buffer contains the matched message. Nonblocking operations return request handles; applications should complete or manage them according to the standard. Persistent communication requests can reduce repeated setup for fixed communication patterns. Collective calls place participation obligations on the group, and nonblocking collectives have analogous completion semantics. When trying overlap, instrument an actual timeline and test whether computation meaningfully proceeds during transfers.

One-sided communication, often called remote memory access, permits processes to expose memory windows and perform operations such as remote get, put or accumulate under synchronization rules. It can be useful for irregular access patterns but shifts complexity from explicit sends and receives to epochs, ordering and visibility. The absence of a matching receive call does not imply that synchronization disappears. Some one-sided patterns reduce overhead while others become harder to reason about than ordinary point-to-point communication. Choose the mechanism based on ownership, traffic patterns and the ability to establish correct memory visibility.

Parallel I/O is another important aspect. If a thousand ranks all open one file and write arbitrary overlapping regions, contention and corruption can arise. Collective file operations and well-defined offsets permit coordinated access. Storing one file per rank can simplify local writes but may overload metadata servers and create thousands of small files. Aggregated I/O combines data into fewer, larger transactions. Compression, checkpoint frequency, and storage system topology further affect the results. The computation's performance profile must include I/O when it is part of the user-visible workload.

A minimal MPI correctness test should run at p=1 and p=2 before scaling further, use small recognizable data, and verify all communication buffers and counts. Test asymmetric message sizes where the algorithm permits them and force large payloads that exceed eager buffering thresholds. Use sanitizers where available and a watchdog timeout to detect hangs in an automated test. A benchmark that only exercises one implementation on one message size cannot validate all message-matching or progress assumptions.

Official API documentation and standard revisions should govern exact function behavior. For teaching, it is more important to explain the lifecycle and ownership rules than to memorize call names in isolation: initialize the environment, identify communicators and ranks, establish data decomposition, perform messages or collectives, validate outputs, and finalize correctly. These principles remain useful even when MPI is wrapped by a higher-level scientific framework.
