# Unit 1: Distributed foundations

## 1.1 Failures and fault models

A distributed service is a collection of independently executing components whose failures are not necessarily visible to their peers. A process that stops replying could have crashed, become overloaded, paused for garbage collection, lost network connectivity, or merely encountered an extremely delayed packet. These explanations produce the same initial observation at a remote caller. The distinction matters because a system that assumes a failed process is permanently dead may elect a replacement while the original is still running. This is how duplicate leaders and duplicated side effects arise. State a fault model before proposing a correctness argument. A crash-stop model assumes a node halts permanently and never sends further messages. A crash-recovery model permits restarting from durable state. An omission model permits lost sends or receives. A Byzantine model permits arbitrary behavior, including contradictory messages sent to different recipients. Each stronger model changes which algorithms and quorums are adequate, as well as the assumptions about trust, authentication, storage, and timing.

Fault tolerance is not the same as preventing all failures. It is the ability to preserve a specified safety or availability property despite a bounded set of failures. Safety says that something bad never occurs, such as two committed owners of the same exclusive lease. Liveness says that something good eventually occurs, such as completing a purchase when enough resources recover. A timeout is evidence for suspicion; it is not proof of failure in an asynchronous network. That is why heartbeat detectors should be described as approximate operational mechanisms, not perfect truth oracles. A service can remain safe while unavailable: rejecting writes after losing a majority can preserve a single authoritative history. It can also remain responsive while violating its intended contract: two isolated replicas might each accept the last seat for a concert. The failure model must cover clients and dependencies, not just servers. A storage backend can make an apparently healthy API unable to confirm a transaction; a DNS failure can make functioning instances unreachable.

Consider a fictional appointment scheduler with nodes A, B, and C in separate availability zones. A holds leadership, and B and C replicate its log. A network split isolates A from B and C, but its process continues running. The service should not treat its local ability to execute code as permission to commit new reservations. If commitment requires acknowledgement from a majority of three voting members, A alone cannot satisfy the rule. B and C may elect a leader if their protocol has the appropriate term and log safety rules. A client still connected to isolated A may observe failed or redirected writes, which is an availability cost with a correctness benefit. If the product allows speculative holds, those must be visibly tentative rather than advertised as confirmed. This example demonstrates that a replica's local uptime and the system's authority to finalize state are separate questions. Nothing about merely placing three copies in three zones automatically ensures consistent decisions.

Engineers often conflate redundancy with independence. Three virtual machines on the same underlying power supply or quota-limited account may fail together. Correlated failure changes the probability model: if all replicas depend on a shared identity service for reauthentication, a failure there can halt writes simultaneously even when their hosts are healthy. The opposite mistake is treating all delays as failures; overly aggressive timeouts can create cascading retries and leader churn. Measure the distribution of legitimate service times, network RTTs, and recovery pauses under load before choosing suspicion thresholds. Separate resource exhaustion from process crash and remote partition in incident reports. When stating resilience claims, identify the fault budget, for example one crash among three voting replicas, rather than the vague phrase 'highly available'. If Byzantine behavior is excluded, say so; authentication does not convert an arbitrary compromise into a harmless crash.

Build a fault-injection laboratory with three simulated nodes, a client, and a directed communication graph. The learner controls whether messages are delayed, lost, duplicated, or reordered, and can crash or restart any process. Instrument a safety assertion that counts confirmed reservations with the same identifier; it must never exceed one. Instrument a liveness probe that asks whether a reservation eventually commits after communication becomes healthy and a majority remains available. Run the same trace with majority-based commitment and with naive local acknowledgement. Compare the point at which the naive version falsely tells clients a booking is final. A clean experiment logs each client response together with the node's term and committed index, rather than relying on animation alone. The simulation deliberately excludes disk corruption, clock hardware faults, and adversarial Byzantine nodes; students must not infer guarantees about those excluded conditions.

## 1.2 Timing models and timeouts

Distributed algorithms need explicit assumptions about message delay and process speed. A synchronous model posits known upper bounds on communication and computation; a partially synchronous model allows useful bounds to emerge eventually or assumes unknown finite bounds; an asynchronous model assumes no known upper bound. These are mathematical models, not marketing adjectives describing whether a code path uses promises or callbacks. In a fully asynchronous setting, a process that has been silent for a long time cannot be distinguished definitively from a slow but correct process. A wall clock is useful for billing or logging but does not establish causal order by itself. NTP-adjusted clocks can jump, while a monotonic clock provides safer elapsed-duration measurement but not a shared global timestamp. An engineer should decide separately what physical-time uncertainty is tolerable, how event ordering is recorded, and which parts of a protocol depend on eventual synchrony.

Suppose a request takes network latency L, remote work time W, and local scheduling delay S. A simple response-time model is T=L+W+S; retries, connection setup, and queueing add further terms. An RPC deadline bounds how long the caller will wait, not how long the remote side will run. If the timeout occurs after the server has committed an operation but before the reply arrives, the client faces an ambiguous outcome. Reissuing a non-idempotent request without an operation identifier can duplicate the effect. A robust API returns durable operation status or accepts a stable idempotency key. Timeout composition also matters. If an upstream request has 500 milliseconds remaining, a downstream call with an independent two-second timeout violates the overall budget. Propagate deadlines and cancel work when safe, while treating cancellation as a request rather than proof that remote effects were undone.

Take a three-tier online assessment service. The gateway gives a request a 900-millisecond budget. It spends 80 milliseconds authenticating, 130 milliseconds looking up the quiz, and 140 milliseconds transferring a response to the grading worker. There are 550 milliseconds left before accounting for queueing and serialization. A worker timeout of 700 milliseconds cannot be justified from the original deadline. If the worker reports a result after the gateway deadline, the response may be lost even though grading completed. Designers should attach a submission identifier and support status retrieval; otherwise students may click Submit again and create multiple grades. Clock skew between hosts should not be subtracted directly from deadlines. Forward a duration or an appropriate monotonic deadline representation using protocol conventions that account for transfer, and trace the elapsed time at each hop.

Aggressive timeouts can appear to improve tail latency while actually degrading a heavily loaded cluster. When callers retry at the same moment, they enlarge the queue that caused the delay; some systems then enter a retry storm. Exponential backoff with jitter distributes arrivals, but adds waiting and cannot guarantee success during a real outage. Hedged requests can reduce latency for idempotent reads when multiple independent replicas exist; they increase system load, so a concurrency cap is necessary. Timeouts should be chosen from measured distributions and service objectives rather than a universal fixed number. A p99 latency is the time below which 99 percent of observed requests fall; it is not a worst-case bound. A p99 measured under light traffic cannot prove a service's behavior at saturation. Read both client-side and server-side histograms, then examine the difference for network and queueing effects.

Implement a timeout explorer where the learner selects nominal RTT, jitter, processing cost, deadline, and retry count. Generate deterministic latency traces with a seeded pseudorandom source, and plot what fraction of requests receives an answer within the deadline. Maintain separate counters for completed operations, acknowledged operations, and abandoned requests. Deliberately inject a lost response after a successful server commit; a visible marker should show why a timeout does not imply rollback. Repeat at a larger client arrival rate and observe how total attempted work can exceed original requests. Ask the student to propose a deadline and retry cap that meet a specified latency budget under the measured workload, then test the choice on an unseen trace. This teaching model abstracts away true operating-system scheduling, network congestion control, and physical clock adjustment.

## 1.3 Message passing and communication contracts

Remote communication uses messages because one process cannot directly read another process's private memory in the ordinary distributed model. A message has a sender, destination, payload, protocol version, identifier, and possible ordering or authentication metadata. Developers must ask which guarantees belong to the application protocol and which are provided by its transport. TCP provides an ordered reliable byte stream while the connection is intact, not an exactly-once transaction protocol. A TCP write returning successfully may mean that bytes entered a local buffer rather than that a remote transaction committed. UDP datagrams may arrive out of order, be duplicated by higher layers, or be lost. HTTP adds request-response semantics but cannot eliminate uncertain outcomes when a response disappears. Reliable delivery claims become meaningful only after the application defines what qualifies as durable acceptance and how acknowledgements are generated.

An at-most-once effect usually means suppressing duplicates even if that means some operations never happen. An at-least-once delivery mechanism may redeliver until acknowledged; consumers must tolerate duplicates. Exactly-once *business effects* can sometimes be engineered using transactional state changes and stable operation identifiers within a specified boundary, but a universal exactly-once network guarantee is not available under arbitrary failures. For a queue consumer processing a payment authorization, the transaction should record both the payment operation identifier and its state change atomically where possible. If a message is acknowledged before committing state, a crash can lose work. If state is committed before acknowledging, a crash can cause redelivery, which the deduplication table must handle. These are observable orderings, not mere implementation details.

In a fictional library inventory system, a checkout service publishes 'loan created' events to a notification worker. The publisher commits a loan record and then crashes before publishing. The record exists, but no email is sent. Reversing the order produces the opposite problem: a notification may announce a loan that the database never committed. A transactional outbox stores the event alongside the loan in one transaction, and a separate relay publishes it. The relay may publish twice if it crashes after sending but before marking the outbox row delivered. Consumers therefore use event IDs and idempotent handlers; the outbox solves atomic recording, not global exactly-once delivery. Alternative designs include log-based change capture. The useful lesson is to trace durable boundaries and crash windows, not to claim that choosing Kafka, RabbitMQ, or another product automatically removes the problem.

Communication design is also a schema-evolution problem. A field added by a new producer may be unknown to an old consumer; a removed field may be required by that consumer. Compatibility rules depend on the serialization format and on whether producers or consumers deploy first. A message envelope should carry a stable type, version or evolution strategy, correlation ID, and trace context where appropriate. Avoid encoding private data in headers that may be copied into logs. Synchronous RPC makes a dependency's availability part of the caller's critical path; asynchronous messaging can decouple arrival from processing but introduces eventual completion, duplicate delivery, queue backlog, and operational requirements. Choose deliberately based on the required user-facing contract, rather than assuming asynchronous always means faster or more reliable.

Create an event-delivery experiment with a producer, durable outbox, relay, queue, and consumer. Controls select crash-after-commit, crash-after-send, acknowledgement loss, and duplicate delivery. Display each stage's durable records and the number of business effects. Invariant one: a committed loan eventually has an event in the outbox. Invariant two: processing the same event identifier repeatedly creates at most one notification job. Show failure traces where naive publish-then-commit or commit-then-publish violates the first invariant. Students should write a small consumer pseudocode handler that checks a unique event key inside the same transaction as its effect, then compare with a handler that checks and writes in separate transactions. The simulation cannot model all broker broker-specific retention and isolation modes, so those must be configured and tested in real deployments.

## 1.4 Consistency and observable histories

A consistency model describes which results a client may observe from concurrent operations; it is not a measure of how many replica copies currently exist. Linearizability requires each operation to appear to take effect at a single point between its invocation and response, while respecting real-time order for non-overlapping operations. Sequential consistency retains some total order consistent with each process's program order but does not necessarily preserve external real-time order. Causal consistency preserves the order of causally related updates, allowing concurrent independent updates to be observed in different orders. Eventual convergence is weaker still: in the absence of new writes, replicas may ultimately agree, but this alone says little about observations during the convergence period. Specify whether the model applies to one key, a transaction, a database snapshot, or an entire service.

Consider a user changing an account email from old@example.org to new@example.org. After receiving a confirmed success response, she reads the account in a new browser tab. If that read returns the old value and the contract promises read-after-write consistency, the implementation has violated an observable guarantee even if all replicas eventually converge. A client could route the subsequent read to the same leader, use a session token representing the committed version, or wait for a follower to catch up. Each mechanism has a failure and latency cost. Concurrent writes complicate matters: last-write-wins based on unsynchronized machine clocks may discard a meaningful update rather than reconcile it. Logical versions or application-specific merge rules are safer for some data types, but they do not automatically satisfy stronger global consistency.

Imagine an online course platform storing seat availability in two regions. Initially one seat remains. A learner in region East and another in region West both request the final seat while inter-region links are broken. If both regions unconditionally accept a local decrement and promise a confirmed enrollment, the system may overbook. A replicated counter that later converges to negative one is not an acceptable repair if the contractual guarantee forbids overselling. A service can instead allocate disjoint regional escrow quotas, require a single authoritative decision, or reject registrations during loss of coordination. Each option changes availability, operational flexibility, or fairness. A useful design review writes the invariant 'confirmed seat count never exceeds capacity' before selecting a replication strategy. That invariant is more informative than declaring that eventual consistency is good or bad.

Consistency costs must be interpreted in context. A product recommendation counter can tolerate temporary divergence, provided totals eventually reconcile. A withdrawal authorization or exclusive membership token usually cannot tolerate contradictory authoritative decisions. Some applications mix models by operation: approximate analytics may read a delayed replica, while critical updates use a quorum or transaction. The phrase CAP theorem is frequently overstated. Under a network partition, a system cannot simultaneously guarantee both linearizable service and availability of every request in all partition components; this does not say that consistency, availability, and partition tolerance are three interchangeable knobs under normal operating conditions. Latency tradeoffs also arise without a partition, as wide-area coordination takes time. Document both normal-case latency and partition behavior for each API.

Design a history-checking lab for a small register supporting read and write operations. The input is a list of invocation times, response times, returned values, and client identities. The student tests whether a legal linearization can fit within each operation's execution interval, rather than merely sorting replies. Include a case where a read returning zero overlaps a write of one; depending on overlap, zero may be valid. Include a separate case where the write completed before the read began; returning zero then violates linearizability. Extend the experiment with a causal chain in which client A creates an item and then shares its identifier; client B should not observe a reply to that item without an appropriate account of the cause. Explain that a finite test history can detect certain violations but cannot prove a general implementation correct across all future executions.

## 1.5 Capstone: a partitioned campus reservation service

A campus reservation service has a deceptively small API: list rooms, hold a room, confirm a reservation, and cancel a reservation. Behind that API are independent frontends, a reservation database, an event pipeline, and a regional routing layer. Define the central invariant before touching architecture: for a particular room and time interval, at most one confirmed reservation may own the resource. Viewing availability is less stringent. The website can show a recently cached timetable, but an authoritative confirmation must consult an owner that can enforce the invariant. The application's states might include AVAILABLE, HOLD_PENDING, CONFIRMED, CANCEL_PENDING, and RELEASED. A failed network response must not quietly cause the application to move from HOLD_PENDING to CONFIRMED in the user's browser. Product language must match durable state. This contract reveals which failures are tolerable for the read path and which require safe rejection of writes.

Start with a single regional leader and two voting followers. The leader assigns a committed sequence to reservation commands and the followers apply the same deterministic transition logic. Clients present an opaque operation key to safely retry when responses disappear. Write the failure model: crash-recovery nodes, lossy and delayed messages, independent disk persistence assumed correct, no Byzantine processes, and quorum-reachable operation needed for authoritative writes. A separately cached search index consumes confirmed-reservation events asynchronously. During a partition that isolates the leader, the database may stop accepting new confirmations from that component, while cached search pages continue to load. That behavior is acceptable if the page does not pretend its stale availability is a promise. A caller can be redirected to a different leader or receive a retryable pending status; in neither case should it receive a false confirmation.

Trace a specific attempt. Student N submits operation key R-104 for a room at 14:00. The leader appends the request at log index 712 and replicates it to a majority, then commits and applies it. The network drops the response. The student retries R-104 against a new frontend which reaches a newly elected leader. The committed state includes the operation key, so the result is the original confirmation rather than a second hold. Another student simultaneously sends R-105 for the same room; the state transition sees the room occupied and rejects it. If the first command had not reached a majority before the leader's crash, a safe new leader might never commit it; the client must query or retry using the same key. This difference between unknown outcome and confirmed outcome is the focus of the case, not the fact that three servers exist.

Now consider external side effects. Confirmation triggers a calendar invitation and an email. If the event dispatcher publishes first and then loses its database connection, the user may receive an invitation to an uncommitted reservation. If the database commits first and the process crashes before publishing, the user may have a valid booking without notification. A transactional outbox records a notification intent in the same transaction as the confirmed state transition. The relay may deliver the event twice; the calendar integration uses a stable event identifier to avoid duplicate invitations when its API supports idempotency. The client-visible booking status must not depend on whether the email system is working. A reliable internal workflow can show 'confirmed, notification pending' without weakening the room allocation invariant. Document this separation in the API schema.

A useful test suite contains several families of traces. Crash the leader before acknowledgement, after quorum replication, and after notifying one client. Delay a follower's messages beyond a timeout while it remains healthy. Duplicate a reservation event, reverse unrelated email messages, and restart a replica from a snapshot whose log index is behind the cluster. For each trace, check the unique-confirmation invariant and whether accepted operation keys eventually return the same result. Track unavailable requests separately from incorrect confirmations. Finally ask whether the product could serve appointments during a full regional partition using preallocated room quotas. Because each room-time slot is indivisible, preallocating exclusive regional ownership might work for selected resources, but would require explicit transfer and timeout policy. The student should justify the chosen recovery and UX contract with evidence from the traces.

## Fully worked questions
### Question 1: Availability under a three-node partition
A three-voter replicated appointment log uses majority commitment and divides into components of one and two voters. Determine which component can confirm a new write and explain what happens if an old leader remains active in the one-voter component.
- For three voters the majority size is floor(3/2)+1=2. An acknowledgement from only one voter is insufficient, regardless of whether that voter previously held leadership.
- The two-voter component can potentially elect a leader and commit after satisfying the protocol’s term and log-up-to-date rules. Mere connectivity does not automatically establish leader election correctness.
- The isolated previous leader must not confirm new writes. A client may experience an unavailable operation, but this preserves the single committed-history invariant.
**Result:** The two-voter partition can progress under a correct protocol; the one-voter partition cannot commit.

### Question 2: Budget a sequence of RPC deadlines
An upstream request has a 900 ms deadline. Authentication takes 80 ms, lookup takes 130 ms, and transfer takes 140 ms. Ignoring additional safety margins, what is the maximum remaining computation budget, and why is a 700 ms downstream timeout unsafe?
- Compute already consumed time: 80+130+140=350 milliseconds.
- Subtract elapsed time from the original budget: 900−350=550 milliseconds.
- A downstream timeout of 700 ms exceeds the remaining 550 ms, so it can outlive the user-facing deadline. Preserve a smaller safety margin for reply transmission and local processing.
**Result:** At most 550 ms remain before additional overhead and safety margins.

### Question 3: Identify a non-linearizable history
Client A completes write(x=1) at time 20. Client B starts read(x) at time 25 and completes at time 30 returning 0. Initially x=0. Is this history linearizable, assuming no other writes?
- Linearizability respects the real-time order of non-overlapping operations. A write that finishes before a read begins must precede it.
- The latest write to x before the read is write(x=1), so a legal sequential register execution returns 1.
- Returning 0 cannot be placed in a total order between invocation and response consistent with this real-time order. A stale eventual replica might return it, but the result is not linearizable.
**Result:** No; the read of 0 violates linearizability.
